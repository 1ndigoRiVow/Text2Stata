# 部署方案

本文件说明 Text2Stata 的两个发行形态、它们为什么这样切，以及云端版的实施路线。

---

## 一、两个版本

| | 本地版 | 云端版 |
|---|---|---|
| 形态 | 解压即用的桌面程序 | 网页，打开网址就能用 |
| 谁运行 Stata | 用户自己的电脑 | 用户自己的电脑 |
| 数据在哪 | 只在本机 | 只在本机（云端只见变量名） |
| 需要额外 Stata 授权 | 不需要 | 不需要 |
| 面向 | 愿意自己动手、需要离线 | 发给你想省事的人 |

两个版本共用同一套分析内核（模板引擎、执行判定、结果校验），差别只在"谁来托管界面和调度"。

---

## 二、本地版为什么不是 Docker

这是设计过程中最先被否掉的方案，值得记下来。

Windows 上的 Docker Desktop 跑的是 **Linux 容器**。容器里的进程：

- 看不到宿主机的 `C:\Program Files\StataNow19\StataSE-64.exe`
- 用不了宿主机的 Windows Stata 授权
- 把 Stata 装进 Linux 容器，又需要另外一套 Linux 授权和安装包

一句话：**容器和宿主机上的 Stata 之间隔着一层操作系统边界，跨不过去。**

所以本地一键包的做法是 **PyInstaller onedir 打包的原生 Windows 程序**：

```
Text2Stata-windows.zip
  └─ Text2Stata/
       ├─ Text2Stata.exe      ← 双击这个
       └─ （Python 运行时与依赖）
```

用户解压 → 双击 exe → 控制台打印访问地址 → 浏览器自动打开。不需要装 Python，不需要配依赖，不需要碰 `.env`。

第一次运行没配密钥时，会直接跳转到设置面板。

## 三、云端版：为什么不让 Stata 跑在云上

### 三条路，只有一条不用额外花钱

| 方案 | Stata 在哪 | 授权 | 结论 |
|---|---|---|---|
| 本地版 | 用户电脑 | 用户自己的单用户授权 | 合法 |
| 私有云 | 你的云主机，只有你访问 | 你的单用户授权 | 合法（Stata 官方博客明确教人这么用） |
| **多人共享云** | 你的云主机，多人访问 | **需要网络授权** | 官方条款不允许单用户授权共享，网络授权要询价、量级五位数美元/年 |
| **云端调度 + 本地执行** | 各用户自己的电脑 | 各自的授权 | 合法，且不需要买任何东西 |

Stata 官方条款的两句话决定了这一切：

> 单用户授权**不得安装在服务器上通过网络共享**
> —— StataNordic 官方 FAQ：*A single-user license may not be installed on a server and shared over a network*

> （官方博客《Stata in the Cloud》）教用户在云主机上安装自己的 Stata 授权，前提是**授权用户是唯一能访问的人**

### 选定的架构

**云端只做控制平面，执行留在用户机器上。**

```
┌──────────────────────────────────────────────────┐
│  云端（你买的服务器）                              │
│    · 网页界面        · 意图解析（调大模型）         │
│    · 账号与邀请      · 模板装配（确定性，出 .do）    │
│    · 任务派发与归档                                │
└──────────────────────────────────────────────────┘
        ▲                                  │
        │ ① 数据描述（变量名 + 标签）        │ ③ .do 脚本
        │ ④ 日志 + 结果摘要                  ▼
┌──────────────────────────────────────────────────┐
│  用户电脑（本地执行代理，装一次）                   │
│    · .dta 数据文件  ← 全程不离开这台机器           │
│    · 本机 Stata     ← 用用户自己的授权              │
└──────────────────────────────────────────────────┘
```

这个切法的三个好处：

1. **不用买 Stata 网络授权**，省掉最大一笔成本，也绕开授权合规问题。
2. **用户数据不出本机**。云服务器上跑的只有"变量名叫什么"这类描述信息，没有数据本体。
3. **云端很轻**。不装 Stata，不跑计算，一台 2 核 4G 的机器足够。

代价是用户仍然要装一次代理程序 —— 这是这个方案唯一没能省掉的步骤。

## 四、需要你拍板的一个问题

**产物文件（回归表 `.rtf`、图表 `.png`、数据 `.csv`）要不要回传云端？**

| | 方案 A：回传 | 方案 B：只留本机 |
|---|---|---|
| 体验 | 网页上统一查看、下载，换台设备也能拿结果 | 网页只显示日志与结果体检，产物去本机取 |
| 数据边界 | 结果数据出域，落在你的服务器上 | 数据完全不出用户机器 |
| 服务器成本 | 需要存储和清理策略 | 几乎为零 |

我倾向 **A 作默认 + 提供 B 的开关**，因为多数人用这个工具就是图"在哪都能拿到结果"，而分析产物通常不算敏感。但如果你的熟人有处理敏感数据的场景，B 是必要的。

## 五、技术选型

### 通信：HTTP 轮询，不用 WebSocket

本地代理每隔一两秒发一个"有我的活吗"的请求，有活就领走。

理由：

- **穿透性好**。代理、防火墙、公司网络对短连接 GET 都放行，长连接经常被掐。
- **断线自恢复**。用户合上笔记本、换个网络，下次轮询自动接上，不需要重连逻辑。
- **好调试**。出问题看 HTTP 请求日志就够了。

任务执行本来就是秒级到十几秒级，轮询引入的延迟可以忽略。WebSocket 在这个场景里是过度设计。

### 状态存储：SQLite

用户、任务、配额三张表就够。单机部署用 SQLite 零运维，后续要扩再换 Postgres。

### 鉴权：邀请码注册 + 会话 Cookie

不做公开注册。你生成邀请码给熟人，对方注册后由你审批。

### 部署：Docker Compose + Caddy

云端**可以**用 Docker（它只跑 Python，不需要 Stata，前面那条限制不适用）。
Caddy 负责 HTTPS，证书自动申请续期，比手写 Nginx 配置省事。

## 六、大模型密钥的双模式

你要的两种都支持，实现上分两处：

| 模式 | 密钥存哪 | 计费 |
|---|---|---|
| 站点密钥 | 服务器配置文件 | 计入用户配额 |
| 自带密钥（BYOK） | **只存在用户浏览器本地**，随请求带上，服务端不落库 | 用户自己承担 |

BYOK 特意不落库：这样"你的密钥会不会被我看到"这个问题有干净的答案 —— 不会，服务端从头到尾没有存过。

## 七、实施阶段

| 阶段 | 内容 | 状态 |
|---|---|---|
| **Phase 0** | 本地一键包：启动器、前端托管、设置面板、Stata 自动探测、打包脚本 | 本轮完成 |
| Phase 1 | 云端骨架：账号、任务表、代理派发协议（先不接大模型，用假计划打通链路） | 待开始 |
| Phase 2 | 本地执行代理：领取任务 → 跑 Stata → 回传结果 | 待开始 |
| Phase 3 | 前端改造：登录、任务列表、云端/本地模式切换 | 待开始 |
| Phase 4 | 双密钥模式 + 配额与限流 | 待开始 |
| Phase 5 | 部署上线：域名、HTTPS、备份、监控 | 待开始 |

Phase 1 和 2 要一起设计：**代理与云端的接口契约先定死，再分别实现**，否则两边会反复返工。

## 八、安全与合规边界

部署云端版之前必须处理的几项：

1. **ICP 备案**。服务器在中国境内、对公众提供服务的，需要备案。只给几个熟人用、不公开宣传，性质上接近私人服务，但既然要买域名和服务器，建议按正规流程走。
2. **CORS 要收紧**。本地版现在是 `origins: "*"`（只监听 127.0.0.1，风险有限）；云端版必须改成白名单域名。
3. **会话 Cookie 必须 `HttpOnly` + `Secure` + `SameSite=Lax`**。
4. **站点密钥必须限流和配额**。挂在公网上的 API 会被扫到，没有配额就是敞开的钱包。
5. **日志脱敏**。用户数据的变量名可能间接暴露研究对象，云端日志不要长期留存 schema 原文。
6. **备份**。SQLite 文件定期冷备，异地存一份。

## 九、已知取舍

- **本地代理仍是一次安装**。比配 Python 环境轻得多，但不是零。真正做到"零安装"必须让 Stata 跑在云上，那就要买网络授权。
- **用户仍需自备 Stata 授权**。这是产品定位决定的 —— 目标用户是"有 Stata 但被命令行卡住的人"，不是"没有 Stata 的人"。
- **云端版的"傻瓜"是有边界的**。它省掉的是环境配置，不是软件本身。
